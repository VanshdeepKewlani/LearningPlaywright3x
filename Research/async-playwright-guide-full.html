Async JavaScript, from callbacks to Promise.race

A working reference for the six building blocks you'll use constantly when writing Playwright tests and automation scripts — with runnable examples, and every pro/con backed by its own short code sample.

1Callback

A callback is a function passed into another function to be run later, usually once some work finishes. It's the original async pattern in JavaScript, predating Promises.

Core example

function loadUser(id, callback) {
  setTimeout(() => {
    const user = { id, name: "Asha" };
    callback(null, user); // (error, result) convention
  }, 500);
}

loadUser(1, (err, user) => {
  if (err) return console.error(err);
  console.log("Loaded:", user);
});

In Playwright

// callback fires every time the page logs to console
page.on('console', msg => console.log(`Page log: ${msg.text()}`));

// callback used to intercept and mock network requests
await page.route('**/api/prices', route => {
  route.fulfill({ json: { price: 42 } });
});
Pros

Handles repeated events naturally

Unlike a Promise (which settles once), a callback can be invoked many times — a great fit for ongoing page events.

page.on('console', msg => {
  // fires on EVERY console.log in the page, indefinitely
  console.log(msg.text());
});

Zero language overhead

No special syntax needed — plain functions work in any JS environment, even very old runtimes.

function retry(fn, times, done) {
  fn((err, result) => {
    if (err && times > 0) return retry(fn, times - 1, done);
    done(err, result);
  });
}
Cons

Callback hell

Nesting callbacks to sequence steps quickly becomes unreadable.

login(user, (err, session) => {
  loadDashboard(session, (err, data) => {
    loadWidgets(data, (err, widgets) => {
      // three levels deep already, and growing
      render(widgets);
    });
  });
});

Inconsistent, manual error handling

The "(err, result)" convention isn't enforced by the language — nothing stops you from forgetting the check.

loadUser(1, (err, user) => {
  // oops — forgot to check `err` here
  console.log(user.name); // throws if err was set and user is undefined
});

No built-in composition

There's no callback equivalent of Promise.all — running things in parallel means hand-rolling a counter.

let remaining = 2, results = {};
loadUser(1, (e, u) => { results.user = u; if (--remaining === 0) done(); });
loadOrders(1, (e, o) => { results.orders = o; if (--remaining === 0) done(); });

2new Promise

new Promise(executor) wraps a one-time async operation. The executor receives resolve and reject, called when the work succeeds or fails.

Core example

function wait(ms) {
  return new Promise((resolve, reject) => {
    if (ms < 0) return reject(new Error("ms must be positive"));
    setTimeout(() => resolve(`waited ${ms}ms`), ms);
  });
}

In Playwright — custom polling

function waitForJobToFinish(jobId) {
  return new Promise((resolve, reject) => {
    const interval = setInterval(async () => {
      const res = await fetch(`/jobs/${jobId}`);
      const { status } = await res.json();
      if (status === 'done') { clearInterval(interval); resolve(status); }
      if (status === 'failed') { clearInterval(interval); reject(new Error('Job failed')); }
    }, 500);
  });
}
Pros

Converts any callback API into an awaitable one

You can "promisify" old-style callback functions so they compose with modern async/await code.

function loadUserAsync(id) {
  return new Promise((resolve, reject) => {
    loadUser(id, (err, user) => err ? reject(err) : resolve(user));
  });
}

const user = await loadUserAsync(1); // now awaitable!

Composable with the whole Promise toolkit

Once wrapped, it plugs straight into Promise.all, Promise.race, and await.

const [a, b] = await Promise.all([wait(100), wait(200)]);
Cons

The "Promise constructor anti-pattern"

Wrapping something that's already a Promise (like fetch or a Playwright call) in new Promise is redundant and error-prone.

// don't do this — fetch() is already a Promise
function getData() {
  return new Promise((resolve, reject) => {
    fetch('/api').then(resolve).catch(reject);
  });
}
// just do: function getData() { return fetch('/api'); }

Forgetting to settle leaves it hanging forever

If no code path calls resolve or reject, the Promise never settles — and any await on it hangs indefinitely.

function buggy() {
  return new Promise((resolve, reject) => {
    if (Math.random() > 0.5) resolve('ok');
    // no else branch — 50% of calls hang forever
  });
}

Async errors inside the executor don't auto-reject

A thrown error inside a setTimeout callback won't be caught by the Promise — you must catch and reject manually.

new Promise((resolve, reject) => {
  setTimeout(() => {
    throw new Error('boom'); // NOT caught — becomes an unhandled exception
  }, 100);
});

3Async

The async keyword marks a function as one that always returns a Promise, and unlocks await inside its body.

async function name() {} const fn = async () => {} test('...', async ({ page }) => {})

In Playwright

test('user can log in', async ({ page }) => {
  await page.goto('https://example.com/login');
  await page.fill('#email', 'user@test.com');
  await page.click('button[type="submit"]');
  await expect(page.locator('.welcome-banner')).toBeVisible();
});
Pros

Async code reads like synchronous code

No .then() chains — each step is a plain statement.

async function checkout(page) {
  await page.click('#add-to-cart');
  await page.click('#checkout');
  return page.locator('#total').textContent();
}

Thrown errors become normal rejected Promises

You can catch async errors with ordinary try/catch, no special API needed.

async function risky() {
  throw new Error('failed');
}

risky().catch(err => console.log(err.message)); // "failed"
Cons

Always returns a Promise, even for trivial values

Callers must remember to await or .then() it — the plain value is never returned directly.

async function getFive() { return 5; }

const x = getFive();
console.log(x); // Promise { 5 } — NOT 5

Encourages accidental serialization

Writing steps one after another with await is easy — but independent work ends up running sequentially instead of in parallel.

// slow: each await blocks the next, even though they're unrelated
const title = await page.title();
const url = await page.url();
// faster: Promise.all([page.title(), page.url()])

Unhandled rejections can fail silently or crash

If nothing awaits or catches the returned Promise, an error can go unnoticed or terminate the process depending on the runtime.

async function run() { throw new Error('oops'); }

run(); // no await, no .catch() — unhandled promise rejection

4await

await pauses execution inside an async function until a Promise settles, then unwraps the resolved value (or throws the rejection).

In Playwright

async function safeLogin(page, creds) {
  try {
    await page.fill('#email', creds.email);
    await page.fill('#password', creds.password);
    await page.click('#submit');
  } catch (err) {
    console.error('Login failed:', err.message);
    throw err;
  }
}
Pros

No more .then() chains

Compare the same logic written both ways.

// with .then() chains
page.goto(url).then(() => page.click('#go')).then(() => page.title());

// with await — flatter and easier to follow
await page.goto(url);
await page.click('#go');
await page.title();

Deterministic step-by-step waits

Each awaited action genuinely finishes before the next line runs, which is what makes Playwright scripts reliable.

await page.click('#submit');
// guaranteed: submit has completed before this line executes
await expect(page.locator('.success')).toBeVisible();
Cons

Sequential awaits waste time on independent work

Awaiting unrelated Promises one at a time adds up their durations instead of overlapping them.

// ~1000ms total (500ms + 500ms, run back-to-back)
await wait(500);
await wait(500);

// ~500ms total — run concurrently instead
await Promise.all([wait(500), wait(500)]);

A missing await is a silent bug

Forgetting await before a Playwright action doesn't throw — the script just races ahead of the browser.

// BUG: missing await — click may fire before navigation resolves
page.click('#submit');
const title = await page.title(); // may read the OLD page's title

5Promise.all

Promise.all runs multiple Promises concurrently and resolves once all succeed — or rejects immediately if any one fails.

In Playwright — action + event pairing

const [popup] = await Promise.all([
  page.waitForEvent('popup'),
  page.click('text=Open in new tab'),
]);
Pros

Real concurrency — faster than sequential awaits

// sequential: ~600ms
const title = await page.title();
const visible = await page.locator('#banner').isVisible();

// parallel: ~300ms
const [title2, visible2] = await Promise.all([
  page.title(),
  page.locator('#banner').isVisible(),
]);

Required pattern for catching triggered events

The listener must be armed before the click fires, or the event can be missed entirely.

const [download] = await Promise.all([
  page.waitForEvent('download'), // armed first
  page.click('text=Export CSV'),   // then triggered
]);
Cons

Fails fast, discarding other results

One rejection rejects the whole thing immediately — you lose the results of Promises that would have succeeded.

try {
  await Promise.all([
    Promise.resolve('ok'),
    Promise.reject(new Error('fail')),
  ]);
} catch (e) {
  console.log(e.message); // "fail" — the 'ok' result is gone
}

Wrong tool when you need every outcome regardless of failure

Use Promise.allSettled instead when partial failures are acceptable.

const results = await Promise.allSettled([
  checkLink('/a'), checkLink('/b'), checkLink('/c'),
]);
// every result is kept, tagged 'fulfilled' or 'rejected'

Misuse can cause race conditions

Running actions that must happen in order concurrently can break the intended sequence.

// BUG: both try to interact with the same field at once
await Promise.all([
  page.fill('#email', 'a@test.com'),
  page.click('#email'), // should have happened BEFORE fill
]);

6Promise.race

Promise.race settles as soon as the first Promise in the array settles — whichever finishes first, resolved or rejected.

In Playwright — custom timeout

function timeout(ms) {
  return new Promise((_, reject) =>
    setTimeout(() => reject(new Error('Timed out')), ms));
}

await Promise.race([
  page.waitForSelector('.results-loaded'),
  timeout(5000),
]);
Pros

Clean, reusable timeout wrapper

function withTimeout(promise, ms) {
  return Promise.race([promise, timeout(ms)]);
}

await withTimeout(page.waitForSelector('.slow-widget'), 3000);

"Whichever comes first" UI logic

const outcome = await Promise.race([
  page.waitForSelector('.dashboard').then(() => 'success'),
  page.waitForSelector('.error-banner').then(() => 'error'),
]);
Cons

Losing Promises keep running

They aren't cancelled — they can still throw unhandled rejections later, after the race is already decided.

await Promise.race([wait(100), wait(5000).then(() => { throw new Error('late fail'); })]);
// race resolves at 100ms, but the 5000ms Promise still rejects later,
// potentially as an unhandled rejection

A losing rejection can still fail the race

If the fastest-settling Promise happens to reject, Promise.race rejects too — even if another entry would have resolved moments later.

const fastFail = new Promise((_, reject) => setTimeout(reject, 50));
const slowSuccess = new Promise(resolve => setTimeout(() => resolve('ok'), 100));

await Promise.race([fastFail, slowSuccess]); // rejects, even though slowSuccess would work

Duplicates Playwright's built-in timeout option

Playwright actions already accept a timeout, so a manual race can be unnecessary extra code.

// simpler — no Promise.race needed
await page.waitForSelector('.results-loaded', { timeout: 5000 });
