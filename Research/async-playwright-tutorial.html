Async JavaScript, Explained: from Callbacks to Promise.race

A full tutorial on the six building blocks of asynchronous JavaScript, written specifically with Playwright test automation in mind. Every concept gets a plain-language explanation, a runnable example, and a set of pros and cons that are each backed by their own short, easy-to-follow code snippet — not just a one-line summary.

1Callback

A callback is simply a function that you pass as an argument into another function, with the understanding that it will be called later rather than immediately. This is the oldest pattern JavaScript has for dealing with asynchronous work, and it existed long before Promises or async/await were introduced to the language. The core idea is that instead of waiting for a result to come back directly, you tell the outer function "here's what to do once you're done," and it calls your function whenever that moment arrives. This can happen once, like when a timer finishes, or it can happen many times, like every time a button is clicked or every time the browser prints something to the console. Understanding callbacks properly is worth the effort because Promises, async/await, and even Playwright's own event-driven APIs are all built as layers on top of this same basic idea.

A simple callback example

In the example below, loadUser simulates a slow operation using setTimeout, and instead of returning the user directly, it accepts a callback function as its second argument. Once the fake "work" is done after 500 milliseconds, it invokes that callback and passes it two things: an error (or null if nothing went wrong) and the actual result. This "error-first" style is a very common convention in older Node.js-style callback code, and you'll still see it if you work with legacy libraries.

function loadUser(id, callback) {
  setTimeout(() => {
    const user = { id, name: "Asha" };
    // call the callback once work is done, error-first style
    callback(null, user);
  }, 500);
}

loadUser(1, (err, user) => {
  if (err) {
    console.error("Something went wrong:", err);
    return;
  }
  console.log("Loaded:", user);
});

Where you'll see callbacks in Playwright

Even though most of the Playwright API returns Promises, callbacks haven't disappeared — they're still the natural choice whenever something can happen more than once, such as page events, or when you want to react to something as it happens rather than wait for a single final result. The two examples below show a console listener, which keeps firing every time the page logs something, and a route handler, which intercepts every matching network request so you can fake its response.

// this callback runs every single time the page calls console.log
page.on('console', msg => {
  console.log(`Page log: ${msg.text()}`);
});

// this callback runs every time a request matching the pattern goes out
await page.route('**/api/prices', route => {
  route.fulfill({ json: { price: 42 } });
});
Pros

1. Callbacks handle repeated events naturally

A Promise can only ever settle once, so it's the wrong tool for something that fires again and again, like console messages or dialog boxes. A callback, on the other hand, is just a plain function reference that Playwright can call as many times as it wants, whenever the matching event occurs. In the example below, the listener will keep printing every console message for as long as the page is open, without you having to set anything up again. This is exactly why Playwright's event system (page.on(...)) is callback-based rather than Promise-based.

page.on('console', msg => {
  // this same function is invoked again and again,
  // once for every console.log call the page makes
  console.log("Console message:", msg.text());
});

// later in the test, any page.evaluate() call that logs something
// will trigger the listener above automatically
await page.evaluate(() => console.log('hello from the page'));

2. Callbacks require no special language features

Because a callback is just a function passed as a regular argument, this pattern works in literally every version of JavaScript, including very old browsers and old Node.js releases that predate Promises entirely. You don't need any special syntax, keywords, or runtime support — just ordinary functions. This makes callbacks a genuinely universal building block, and it's why so many older libraries (and some newer low-level APIs) still expose callback-based interfaces rather than Promise-based ones.

function retry(action, timesLeft, onDone) {
  action((err, result) => {
    if (err && timesLeft > 0) {
      console.log(`Retrying, ${timesLeft} attempts left...`);
      return retry(action, timesLeft - 1, onDone);
    }
    onDone(err, result);
  });
}
Cons

1. Deeply nested callbacks become hard to read ("callback hell")

The moment you need to run several asynchronous steps one after another, each depending on the result of the last, callback-based code starts nesting deeper and deeper. Each new step adds another level of indentation, another closing brace, and another place where something can silently go wrong. In the example below, logging in, loading a dashboard, and loading widgets are three separate steps, but they end up nested three levels deep — and a real app would likely need even more steps than this.

login(user, (err, session) => {
  if (err) return console.error(err);

  loadDashboard(session, (err, data) => {
    if (err) return console.error(err);

    loadWidgets(data, (err, widgets) => {
      if (err) return console.error(err);
      // three levels deep already, and a real flow would go deeper
      render(widgets);
    });
  });
});

2. Error handling is manual and easy to get wrong

The "error-first" convention shown earlier is just a convention — nothing in the language forces you to check the err parameter before touching the result. This means it's entirely possible to forget the check, especially in a rush, and your code will happily try to use a result that doesn't exist. In the example below, the missing check means that if loadUser ever calls back with an error, the very next line will throw a confusing "cannot read property of undefined" error instead of a clear message about what actually went wrong.

loadUser(1, (err, user) => {
  // bug: forgot to check `err` before using `user`
  console.log("Name is:", user.name);
  // if err was set, `user` is likely undefined here,
  // and this line throws a confusing runtime error
});

3. There's no built-in way to run multiple callbacks in parallel

Promises have Promise.all to wait for several operations at once, but plain callbacks have no equivalent built into the language. If you want to start two callback-based operations at the same time and only continue once both are finished, you have to build that coordination yourself, usually with a manual counter like the one below. This is not only extra boilerplate, it's also a common source of bugs if the counter logic is even slightly wrong.

let remaining = 2;
const results = {};

loadUser(1, (err, user) => {
  results.user = user;
  if (--remaining === 0) console.log("Both done:", results);
});

loadOrders(1, (err, orders) => {
  results.orders = orders;
  if (--remaining === 0) console.log("Both done:", results);
});

2new Promise

A Promise is an object that represents the eventual result of an asynchronous operation, and it can be in one of three states: pending, fulfilled, or rejected. You create one from scratch using new Promise(executor), where the executor is a function that immediately receives two functions of its own, conventionally named resolve and reject. You call resolve(value) when the operation succeeds and you want to hand back a value, and you call reject(error) when something goes wrong and you want to signal failure. Once a Promise is created this way, it behaves exactly like any other Promise in the language — you can chain .then() onto it, await it inside an async function, or pass it into Promise.all and Promise.race. The main real-world use case for new Promise is "promisifying" an older callback-based function so that it fits into modern async/await code.

A basic example: a custom delay function

Here, wait wraps setTimeout, which is itself a callback-based browser API, inside a Promise. After the specified number of milliseconds passes, the executor calls resolve with a message, which is what any code that awaits or chains onto wait(...) will eventually receive. Notice that if the input is invalid, the executor calls reject instead, immediately turning the Promise into a rejected one.

function wait(ms) {
  return new Promise((resolve, reject) => {
    if (ms < 0) {
      return reject(new Error("ms must be positive"));
    }
    setTimeout(() => {
      resolve(`waited ${ms}ms`);
    }, ms);
  });
}

wait(1000).then(message => console.log(message));

Using new Promise for custom polling in Playwright

Playwright doesn't know how to wait for things outside the browser, such as a background job finishing on your server, so sometimes you need to build your own waiting logic. The function below polls an endpoint every 500 milliseconds using setInterval, and resolves or rejects the Promise depending on the job's status, clearing the interval either way so it doesn't keep running forever.

function waitForJobToFinish(jobId) {
  return new Promise((resolve, reject) => {
    const interval = setInterval(async () => {
      const res = await fetch(`/jobs/${jobId}`);
      const { status } = await res.json();

      if (status === 'done') {
        clearInterval(interval);
        resolve(status);
      } else if (status === 'failed') {
        clearInterval(interval);
        reject(new Error('Job failed'));
      }
      // otherwise, do nothing and let the interval poll again
    }, 500);
  });
}

// used inside a Playwright test after starting a background job
await page.click('#start-job');
await waitForJobToFinish('job-123');
Pros

1. It converts old callback-based APIs into modern awaitable ones

Plenty of older libraries and browser APIs still expect you to pass a callback rather than return a Promise, which means you can't directly use await with them. Wrapping such a function inside new Promise lets you call resolve when the callback succeeds and reject when it reports an error, effectively translating the old style into the new one. Once wrapped like this, the function behaves exactly like any native Promise-returning function, and you can use await on it directly. This pattern, sometimes called "promisifying," is one of the most common reasons developers reach for new Promise in real projects.

function loadUserAsync(id) {
  return new Promise((resolve, reject) => {
    loadUser(id, (err, user) => {
      if (err) reject(err);
      else resolve(user);
    });
  });
}

// now this old callback-based function can be awaited directly
const user = await loadUserAsync(1);
console.log(user.name);

2. Once wrapped, it plugs directly into the whole Promise toolkit

A Promise created with new Promise is not a special or limited kind of Promise — it's exactly the same thing you get back from fetch() or any async function. That means it can be passed straight into Promise.all, raced with Promise.race, or awaited inside a try/catch block just like anything else. This composability is valuable because it means you only need to write the "bridging" code once, and after that you get to use every other async tool in the language on top of it.

// wait(...) returns a real Promise, so it composes with Promise.all
const [first, second] = await Promise.all([
  wait(100),
  wait(200),
]);
console.log(first, second);
Cons

1. Wrapping something that's already a Promise is a well-known anti-pattern

A very common mistake, especially among developers new to Promises, is wrapping a function that already returns a Promise (like fetch, or basically any Playwright method) inside yet another new Promise. This adds an unnecessary extra layer, makes the code longer and more confusing than it needs to be, and introduces more places where you could accidentally swallow an error or forget to reject properly. The fix is almost always to just return the existing Promise directly, or chain .then() onto it, rather than manually re-wrapping it.

// don't do this: fetch() already returns a Promise
function getDataBad() {
  return new Promise((resolve, reject) => {
    fetch('/api')
      .then(res => resolve(res))
      .catch(err => reject(err));
  });
}

// do this instead — no wrapping needed at all
function getDataGood() {
  return fetch('/api');
}

2. Forgetting to call resolve or reject leaves the Promise hanging forever

Because you are manually responsible for calling resolve or reject inside the executor, it's entirely possible to write a code path that does neither. When that happens, the Promise simply stays "pending" forever, and any code that awaits it will hang indefinitely with no error and no timeout, which can be very confusing to debug. In the example below, if the random check fails, there's no else branch, so roughly half the calls to buggy() will never resolve or reject at all.

function buggy() {
  return new Promise((resolve, reject) => {
    if (Math.random() > 0.5) {
      resolve('ok');
    }
    // bug: no "else" branch here — the other 50% of calls
    // never call resolve or reject, so they hang forever
  });
}

3. Errors thrown asynchronously inside the executor are not automatically caught

The Promise constructor will automatically catch errors that are thrown synchronously, directly inside the executor function, and turn them into a rejection for you. However, if the error is thrown later, inside an asynchronous callback like a setTimeout handler, the Promise machinery has no way of knowing about it — the throw happens outside of the constructor's own try/catch logic. In the example below, the thrown error inside setTimeout is not converted into a rejection; instead, it becomes an unhandled exception that can crash a script or silently disappear.

new Promise((resolve, reject) => {
  setTimeout(() => {
    throw new Error('boom');
    // this throw happens inside a later, separate callback,
    // so it is NOT automatically turned into a rejection
  }, 100);
});

3Async

The async keyword is placed in front of a function definition to mark it as an asynchronous function, and it changes how that function behaves in two important ways. First, it guarantees that the function will always return a Promise, even if you write a plain return statement with a simple value inside it — JavaScript automatically wraps that value in a resolved Promise for you. Second, it unlocks the ability to use the await keyword anywhere inside that function's body, which is what lets you write asynchronous logic that reads like ordinary, top-to-bottom synchronous code. You'll see async everywhere in Playwright, because every test function, hook, and fixture callback is written as an async function so that it can use await on Playwright's Promise-based API.

async function name() {} const fn = async () => {} test('...', async ({ page }) => {})

A typical Playwright test written as an async function

In this example, the entire test body is wrapped in an async function so that each Playwright action — navigating, filling a form, clicking a button — can be awaited in sequence. Without the async keyword here, using await anywhere inside this function would be a syntax error, since await is only legal inside functions explicitly marked as async (or at the top level of a module).

const { test, expect } = require('@playwright/test');

test('user can log in', async ({ page }) => {
  await page.goto('https://example.com/login');
  await page.fill('#email', 'user@test.com');
  await page.fill('#password', 'secret');
  await page.click('button[type="submit"]');

  await expect(page.locator('.welcome-banner')).toBeVisible();
});
Pros

1. Asynchronous code ends up reading like ordinary synchronous code

Before async/await existed, chaining several asynchronous steps together meant writing a series of nested or chained .then() calls, which could get visually messy fast. With an async function, you can instead write each step as its own line with await in front of it, and the function will pause at each line until that step finishes, before moving to the next. This makes the control flow much easier to follow at a glance, especially for people who are more used to reading traditional, line-by-line synchronous code.

async function checkout(page) {
  await page.click('#add-to-cart');
  await page.click('#checkout');
  const total = await page.locator('#total').textContent();
  return total;
}

2. Thrown errors automatically become normal, catchable rejections

If you write a plain throw statement anywhere inside an async function, JavaScript doesn't let that error crash the function immediately the way it would in regular synchronous code. Instead, it automatically converts that thrown error into a rejected Promise, which means the caller can handle it using either a regular try/catch block around an await, or a .catch() attached to the function's returned Promise. This unifies error handling for sync-style mistakes and genuinely async failures under the same familiar mechanism.

async function risky() {
  throw new Error('failed');
}

risky()
  .then(() => console.log('succeeded'))
  .catch(err => console.log('caught:', err.message)); // "caught: failed"
Cons

1. The return value is always a Promise, even for trivial values

Because async functions always return a Promise, calling one directly and expecting to immediately get back a plain value will not work the way you might expect from regular functions. In the example below, getFive() looks like it should just return the number 5, but what you actually get back is a pending Promise object, and you need to either await it or chain .then() onto it to access the real value. This can surprise developers who are new to async/await and forget this rule.

async function getFive() {
  return 5;
}

const x = getFive();
console.log(x);          // logs: Promise { 5 }  —  NOT the number 5

const y = await getFive();
console.log(y);          // logs: 5  —  this is the correct way to get the value

2. It's easy to accidentally serialize work that could run in parallel

Because writing one await after another is so natural inside an async function, it's very easy to end up running operations one at a time even when they don't actually depend on each other. Each await pauses the whole function until that specific line finishes, so if you have two independent Playwright calls back to back, you're needlessly waiting for the first to fully complete before even starting the second. The fix, shown in the comment below, is to launch independent operations together and only await once, typically with Promise.all.

// slower: title() finishes fully before url() even starts,
// even though these two calls have nothing to do with each other
const title = await page.title();
const url = await page.url();

// faster: both start at roughly the same time
// const [title, url] = await Promise.all([page.title(), page.url()]);

3. Unhandled rejections can crash a script or fail silently

If an async function throws an error and nothing ever awaits it or attaches a .catch() to its returned Promise, that rejection becomes an "unhandled promise rejection." Depending on the JavaScript environment you're running in, this can print a scary-looking warning, silently do nothing at all, or in some Node.js configurations even crash the entire process. In the example below, calling run() without awaiting it or catching its result means the thrown error has nowhere to go.

async function run() {
  throw new Error('oops');
}

// bug: no `await`, no `.catch()` — this becomes
// an unhandled promise rejection that's easy to miss
run();

4Await

The await keyword can only be used inside a function marked async (or at the top level of certain module setups), and its job is to pause the execution of that function until the Promise placed after it settles. Once the Promise resolves, await "unwraps" it and gives you back the plain value directly, as if the asynchronous work had never happened at all from the point of view of your code. If the Promise instead rejects, await throws that rejection as a regular JavaScript error at that exact line, which means you can catch it using a completely ordinary try/catch block. This is what makes await so powerful for Playwright specifically: browser actions like clicking, typing, and navigating all take an unpredictable amount of time, and await guarantees your test won't move on to the next line until the current action has genuinely finished.

Sequential steps and error handling together

The function below shows both core aspects of await at once: each Playwright action is awaited in order, guaranteeing the fill on email happens before the fill on password, which happens before the click. The whole sequence is also wrapped in a try/catch block, so if any single awaited step throws (for example, because the selector wasn't found), the catch block runs and logs a clear message before re-throwing the error.

async function safeLogin(page, creds) {
  try {
    await page.fill('#email', creds.email);
    await page.fill('#password', creds.password);
    await page.click('#submit');
  } catch (err) {
    console.error('Login failed:', err.message);
    throw err;
  }
}
Key rule Forgetting await before a Playwright action doesn't cause an immediate crash — it just means the next line of your test runs before the browser has actually finished the previous step, which is one of the single most common causes of flaky, unreliable Playwright tests.
Pros

1. It eliminates deeply nested or chained .then() calls

Before await, sequencing three or four asynchronous Playwright steps meant chaining multiple .then() calls together, which can be visually cluttered and harder to scan quickly, especially once error handling is layered in on top. With await, each step becomes its own plain statement, and the overall shape of the function ends up looking almost identical to synchronous code. The comparison below shows the exact same three steps written both ways, side by side, so you can see how much flatter the await version is.

// written with .then() chains
page.goto(url)
  .then(() => page.click('#go'))
  .then(() => page.title())
  .then(title => console.log(title));

// the same logic written with await — flatter and linear
await page.goto(url);
await page.click('#go');
const title = await page.title();
console.log(title);

2. Every awaited step is guaranteed to finish before the next one runs

This might sound obvious, but it's actually the entire reason Playwright tests are reliable at all: the browser needs real time to click things, load pages, and update the DOM, and await makes your test code wait for that real time to pass. Without this guarantee, your test script (which runs extremely fast) would race far ahead of the browser (which does not), leading to assertions that check for things before they actually exist yet. The example below shows a click followed immediately by an assertion, where await ensures the click has truly completed first.

await page.click('#submit');
// because the line above was awaited, we can be confident
// the click has genuinely completed before this next check runs
await expect(page.locator('.success')).toBeVisible();
Cons

1. Awaiting independent operations one by one wastes real time

Each time you write await somePromise(), your function genuinely pauses until that specific Promise settles before moving to the very next line, even if the next line's work has nothing to do with the first. If you have two unrelated delays or requests and await them back-to-back, their durations simply add together, when they could have run side by side instead. The timing comment in the example below spells out exactly how much slower the sequential version is compared to running both concurrently.

// sequential: roughly 500ms + 500ms = ~1000ms total,
// because the second wait() doesn't even start until the first finishes
await wait(500);
await wait(500);

// concurrent: roughly 500ms total, because both start immediately
// await Promise.all([wait(500), wait(500)]);

2. A missing await fails silently instead of throwing an error

If you simply forget to type await before a Promise-returning call, JavaScript does not raise any kind of warning or error about it — the code is perfectly valid syntax, it just doesn't behave the way you probably intended. The Promise starts running in the background, but your function moves straight on to the next line without waiting for it to finish, which in Playwright means the browser action may not have completed yet by the time you check its result. This kind of bug is notoriously hard to spot by reading the code, since it looks correct at a glance.

// bug: missing await before click() means the click is only
// "started", not necessarily finished, by the time the next line runs
page.click('#submit');
const title = await page.title();
// title may reflect the OLD page, if the click triggers navigation
// that hasn't actually completed by the time title() runs

5Promise.all

Promise.all takes an array of Promises and returns a single new Promise that resolves once every Promise in that array has resolved successfully, giving you back an array of their results in the same order you passed them in. If even one of the Promises in the array rejects, however, Promise.all immediately rejects as well, using that same rejection reason, without waiting for the rest to finish. This "run everything at once, but fail fast on the first error" behavior makes it ideal for two very different situations in Playwright: running several independent checks concurrently to save time, and — perhaps more importantly — capturing an event that a click or action is about to trigger, since you must start listening for the event before you perform the action that causes it.

The classic Playwright pattern: pairing an action with the event it triggers

Many Playwright interactions cause something else to happen, such as a new browser tab opening or a file starting to download, and Playwright represents each of these as an event you can wait for with methods like waitForEvent. The tricky part is that if you click first and only start waiting for the event afterward, there's a real chance the event fires before your listener is even attached, and you'll miss it entirely. Wrapping both calls together inside Promise.all solves this: both Promises start running at essentially the same moment, so the listener is guaranteed to be armed before the click is dispatched.

// waiting for a new tab/popup that opens because of this click
const [popup] = await Promise.all([
  page.waitForEvent('popup'),   // listener is armed first
  page.click('text=Open in new tab'), // then the click happens
]);

// the exact same pattern works for file downloads
const [download] = await Promise.all([
  page.waitForEvent('download'),
  page.click('text=Export CSV'),
]);
Pros

1. Genuine concurrency makes independent checks noticeably faster

When you have several async operations that don't depend on each other's results, running them with Promise.all means they all start at roughly the same time and run alongside one another, rather than one strictly after the next. The total time taken ends up being close to the duration of the single slowest operation, instead of the sum of every operation added together. In the timed comparison below, running two checks with plain sequential await calls takes noticeably longer than running the exact same two checks together with Promise.all.

// sequential: total time is roughly title-time + visible-time added together
const title = await page.title();
const visible = await page.locator('#banner').isVisible();

// concurrent: total time is roughly the SLOWER of the two, not the sum
const [title2, visible2] = await Promise.all([
  page.title(),
  page.locator('#banner').isVisible(),
]);

2. It's the required pattern for reliably catching triggered events

As explained above, some Playwright events fire so quickly after the action that causes them that clicking first and then calling waitForEvent afterward risks missing the event completely, especially in fast or automated environments. By starting the wait and the action inside the same Promise.all call, both Promises are created and begin running in the same synchronous tick of the event loop, guaranteeing the listener is ready before the triggering action fires. This pattern shows up constantly in real Playwright test suites for navigation, popups, downloads, and dialogs.

// waiting for navigation that happens because of this click
const [response] = await Promise.all([
  page.waitForNavigation(),
  page.click('text=Next page'),
]);
console.log('Navigated to:', response.url());
Cons

1. It fails fast and discards the results of everything else

The moment any single Promise in the array rejects, Promise.all immediately rejects too, and it does not wait around for the other Promises to finish or give you access to their eventual results, even if some of them would have succeeded. This means that in a batch of, say, five checks where only one fails, you lose visibility into whether the other four passed or failed, which can make debugging test failures more confusing than it needs to be. The example below demonstrates this: even though the first Promise resolves successfully, that successful result is thrown away once the second one rejects.

try {
  const results = await Promise.all([
    Promise.resolve('ok'),
    Promise.reject(new Error('fail')),
  ]);
} catch (e) {
  console.log(e.message);
  // only prints "fail" — the successful "ok" result
  // from the first promise is completely lost
}

2. It's the wrong tool when you need every outcome, pass or fail

Sometimes you genuinely want to know the result of every operation in a batch, including which ones failed and why, rather than stopping at the very first failure. For that situation, Promise.all is actually the wrong choice, and JavaScript provides a very similar-looking sibling method called Promise.allSettled specifically for this purpose. It waits for every Promise to settle one way or the other, and gives you back an array of result objects, each tagged as either fulfilled or rejected, so nothing gets silently discarded.

const results = await Promise.allSettled([
  checkLink('/a'),
  checkLink('/b'),
  checkLink('/c'),
]);

results.forEach(r => {
  if (r.status === 'fulfilled') console.log('OK:', r.value);
  else console.log('FAILED:', r.reason.message);
});

3. Using it on operations that must happen in order can create race conditions

Promise.all is meant for genuinely independent operations, and using it for actions that actually need to happen in a specific sequence can introduce subtle race conditions in your tests. In the buggy example below, both a fill and a click are launched at the same moment, but the click was really meant to happen before the fill (to focus the field first) — by running them concurrently instead of sequentially, their actual order becomes unpredictable, which can lead to flaky, hard-to-reproduce test failures.

// bug: these two actions need to happen in order,
// but Promise.all runs them at roughly the same time instead
await Promise.all([
  page.fill('#email', 'a@test.com'),
  page.click('#email'), // meant to focus the field FIRST
]);
// fix: use two separate awaited statements instead, in the right order

6Promise.race

Promise.race also takes an array of Promises, but unlike Promise.all, it settles as soon as the very first Promise in that array settles, regardless of whether that first one resolves or rejects. Every other Promise in the array keeps running in the background, but their eventual outcomes are simply ignored by the race itself once a winner has already been decided. This behavior makes Promise.race the natural tool for "whichever happens first" logic, most commonly used to implement custom timeouts around operations that might otherwise take too long, or to detect which of two different possible outcomes occurs first on a page.

Adding a custom timeout to a slow operation

The timeout helper below returns a Promise that does nothing but wait for a fixed amount of time and then reject with a timeout error. By racing this against a real Playwright wait, whichever one finishes first determines the outcome: if the selector appears quickly, the race resolves normally, but if it takes too long, the timeout Promise rejects first and the whole race rejects with a clear "Timed out" error instead of hanging indefinitely.

function timeout(ms) {
  return new Promise((_, reject) => {
    setTimeout(() => reject(new Error('Timed out')), ms);
  });
}

async function waitForElementOrTimeout(page) {
  return Promise.race([
    page.waitForSelector('.results-loaded'),
    timeout(5000),
  ]);
}

try {
  await waitForElementOrTimeout(page);
} catch (err) {
  console.log('Either the selector or the timeout lost the race:', err.message);
}
Pros

1. It gives you a clean, reusable way to add timeouts to any Promise

Because Promise.race doesn't care what kind of Promises you give it, you can write one small helper function like withTimeout below and reuse it around any asynchronous operation in your codebase, not just Playwright actions. This keeps your timeout logic centralized in one place rather than duplicated everywhere you need it, and it makes the intent of your code very readable: "do this thing, but give up after this long."

function withTimeout(promise, ms) {
  return Promise.race([promise, timeout(ms)]);
}

// reused for a totally different, slow-loading widget
await withTimeout(page.waitForSelector('.slow-widget'), 3000);

2. It's a natural fit for "whichever outcome happens first" UI logic

Sometimes a page can end up in one of two (or more) different states depending on what happens, such as a login either succeeding and showing a dashboard, or failing and showing an error banner, and you genuinely don't know in advance which one will occur. Promise.race lets you wait for both possibilities simultaneously and simply act on whichever one actually shows up first, without needing to guess or poll manually.

const outcome = await Promise.race([
  page.waitForSelector('.dashboard').then(() => 'success'),
  page.waitForSelector('.error-banner').then(() => 'error'),
]);

console.log('Login outcome was:', outcome);
Cons

1. The losing Promises are not cancelled — they keep running

JavaScript's Promises have no built-in cancellation mechanism, so when Promise.race "picks a winner," the other Promises in the array don't actually stop; they simply continue running to completion in the background, completely detached from the race's own result. If one of those losing Promises eventually rejects after the race has already resolved, that rejection can surface later as an unhandled promise rejection, which is easy to miss since your code has already moved on. The example below illustrates this: the race itself resolves quickly, but the slower Promise still rejects afterward, on its own schedule.

const slowFailure = wait(5000).then(() => {
  throw new Error('late failure');
});

await Promise.race([wait(100), slowFailure]);
// the race resolves after ~100ms using the fast promise, but
// slowFailure keeps running and still rejects ~5000ms later,
// potentially as an unhandled rejection nobody is listening for

2. If the fastest Promise happens to reject, the whole race rejects too

"Winning" the race doesn't mean "succeeding" — it just means settling first, and settling can mean either resolving or rejecting. If the quickest Promise in the array happens to be one that fails, Promise.race will reject with that failure immediately, even if a different, slightly slower Promise in the same array would have gone on to resolve successfully just moments later. The example below shows exactly this scenario: a fast-failing Promise beats a slower successful one, so the overall race ends in rejection despite a valid success being only 50 milliseconds away.

const fastFail = new Promise((_, reject) => {
  setTimeout(() => reject(new Error('fast failure')), 50);
});
const slowSuccess = new Promise(resolve => {
  setTimeout(() => resolve('ok'), 100);
});

try {
  await Promise.race([fastFail, slowSuccess]);
} catch (e) {
  console.log(e.message);
  // prints "fast failure", even though slowSuccess
  // would have resolved successfully just 50ms later
}

3. It often duplicates timeout behavior Playwright already provides

Most Playwright actions and assertions already accept their own timeout option directly as part of their normal call signature, meaning you often don't need to build a manual Promise.race timeout at all. Reaching for Promise.race in these cases adds extra code, an extra helper function, and an extra thing to maintain, when a single built-in option would achieve exactly the same result far more simply.

// unnecessary: manually racing against a custom timeout helper
await Promise.race([
  page.waitForSelector('.results-loaded'),
  timeout(5000),
]);

// simpler: Playwright already supports a timeout option directly
await page.waitForSelector('.results-loaded', { timeout: 5000 });
